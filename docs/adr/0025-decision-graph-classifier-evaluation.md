# 0025: 決定グラフの分類は規則を維持し、BERT・Jev・GiNZA は当面採用しない。評価は発話単位のラベルで行う

Date: 2026-10-04
Status: accepted（決定1〜4）。「保留した判断」は提案であり、決定ではない。

## 背景

決定グラフ（`src/utils/meetingDecisionGraph.ts`）は、発言を正規表現で種類（`risk` / `problem` / `reason` など）と状態（`unconfirmed` など）に分けている。
推測・可能性の表現の拾い方が言い回しに依存し、ほぼ同じ意味でも結果が変わった
（「落ちる可能性があります」は拾い、「落ちるおそれがあります」「落ちると思います」は拾わなかった）。

この課題を直す過程で、次の2点が問題になった。

1. 既存の `npm run semantic:eval`（20ケース・24発話）は、この課題を測れなかった。
   - 採点対象は決定とアクションの**件数**だけで、リスク・理由・問題・未確認は採点されない。
   - 推測表現を含む発話が1つもない。
   - 100% と表示される列は `core`（Semantic Core の sidecar）で、今回直した `meetingDecisionGraph.ts` は `legacy` 列である。
   - したがって「`semantic:eval` が悪化しない」は、この変更の品質の裏付けにならない。
2. 「規則では限界があるのではないか」という疑問から、BERT 系・Jev・GiNZA を検討した。

## 決定

1. **推測の判定は規則で行い、`isHedged`（`src/utils/hedgedExpression.ts`）に集約する。**
   - 語尾を正規化（です・ます・ません）し、「と思う／と思います」「かもしれない／かもしれません」「考えられる」「おそれ」「のでは」「かと」「落ちそう」を同じに扱う。
   - 「いいと思う」は評価であり推測ではない、という既存の例外は維持する。
2. **推測を含む発言の種類は、内容で分ける。**
   - 悪い結果（落ちる・壊れる・遅れる・止まる・失敗・エラー）の推測は、未確認の `risk`。
   - 推測だけでは `reason` にも `evidence` にもしない。種類が決まらないものは発言のまま残す。
   - 推測を含む発言は決定にしない（[ADR 0018](0018-meeting-state-primary-surface-and-epistemic-boundaries.md) の境界）。
   - 悪い結果の語や問題の語に直接かかる否定は、種類を断定せず発言のまま残す。
   - 「不足」は悪い結果ではなく問題として扱う。
3. **Jev は採用しない。BERT 系の学習ベースの分類も、当面採用しない。Python（GiNZA）のバックエンドも、当面採用しない。** 根拠は次節。
4. **評価は、発話単位のラベル付きデータで行う。**
   - 1発話ごとに、期待するノード（`risk:unconfirmed` など）と完全一致するかを採点する（`npm run decision:eval`）。
   - 規則を直すための開発用データと、直したあとに1回だけ流す未使用データを分ける。未使用データは、流した時点で使い切りとなる。
   - ラベル付きデータ（LLM で生成したダミー）は、リポジトリに含めない（`eval-data/`、gitignore）。

## 検討した選択肢と結果

測定は、すべて**ラベル未確認または LLM 生成のダミーデータ**で、件数が少ない。数ポイントの差は誤差であり、順位づけには使えない。

### 規則（採用）

| データ | 直す前 | 直した後 |
|---|---|---|
| 開発用 55発話（規則を直すときに見ていた。ラベルは作成者が確認） | 50/55（91%） | 54/55（98%） |
| 未使用 25発話（直したあとに初めて流した） | 未測定 | 22/25（88%） |

- 開発用の数字は、見ていたデータでの数字なので、汎化性能を過大に示す。未使用データの88%が、より正直な値である。
- 未使用データの不一致3件は、悪い結果の語彙の漏れ（「足りなくなる」「減る」）だった。
- 開発用の不一致1件は、「先にテストを書きましょう」が提案として拾えないこと。提案パターンが「しましょう」系に限られており、推測とは無関係の既存の穴である。

### BERT 系（保留）

- ブラウザ（transformers.js）で、量子化した日本語 BERT と多言語の e5-small が動くことは確認した。
  - 1発話あたり、ブラウザ（WASM）で ja-bert 約47ms・e5-small 約13ms（ヘッドレス環境、ウォーム時の中央値）。
  - 日本語 BERT は公開モデルにトークナイザがなく、語彙ファイルから自作した。本来の MeCab 分かち書きは再現していない。
- 開発用 55発話での leave-one-out（1件ずつ外して残りで学習）の完全一致率は、最良で 63.6%（e5-small・ロジスティック回帰）。ja-bert は 50.9%。多数派（「なし」）を常に出す基準は 40.0%。
  - 「推測を含むか」は拾えたが、提案・質問・決定・理由の区別は当たらなかった。
  - 原因は、8クラスに対して学習データが少なすぎること（少数クラスは1〜5件）。手法の限界とは言えない。
- 結論: ラベル付きの実データがない段階では、規則の置き換えにならない。

### Jev（不採用）

- TypeSafe AI（2026-09）の判断専用モデル。文と型付きの質問を入れると、回答と較正済みの確率を返す。
- **API 専用でクローズドソース**。[AGENTS.md](../../AGENTS.md) の「クラウド AI API は追加しない」に反する。
- 日本語対応は公式に記載がなく、Jev 系 OSS の日本語300件の検証記事では、真偽判定が多数派ベースラインを下回った。
- 以上は二次情報（解説記事）の自己申告であり、私たちは測っていない。出典: [ml6 の比較](https://ml6.eu/en/blog/jev-vs-gpt-6-luna-vs-bert-text-classification)、[Laya の日本語検証](https://zenn.dev/genelab_999/articles/533144853290a7)、[JEV vs BERT](https://daily.dev/posts/jev-vs-bert-what-s-actually-different--9ngceslfr)。

### GiNZA + spaCy のルールベース（保留）

別の検証プロジェクト（リポジトリ外）で、`ja_ginza` の形態素・係り受けによる分類器を作って比べた。

| データ | 本体の規則（直す前） | 本体の規則（直した後） | GiNZA |
|---|---|---|---|
| 開発用 55発話 | 50（91%） | 54（98%） | 55（100%、dev に合わせて調整済み） |
| 別に作った 40発話（未調整・ラベル未確認） | 21（53%） | 27（68%） | 31（78%） |

- 本体の規則を直すときは、開発用の不一致の原因だけを直し、40発話の不一致は見なかった。GiNZA は提案・疑問・決定の規則も含めて作られており、同じ条件の比較ではない。
- GiNZA の改善の大半（否定・活用形）は、本体の正規表現に小さな規則（約25行・新規依存なし）を足すだけで取れた。
- 名詞化された否定（「壊れる心配はありません」型の一部）や、語彙の漏れは、GiNZA でも残った。
- 常駐のコスト: 依存が約370MB、メモリが約0.5GB。処理時間は約2ms で、リアルタイムの予算（[ADR 0023](0023-realtime-first-semantic-core-fast-and-refinement-paths.md)）の約1.6%。
- AGENTS.md は Python を禁止している。取り込むには、方針の変更か別リポジトリ化の判断が先に必要で、ブラウザだけで動く公開デモとも相性が悪い。

## ライブラリで改善できる範囲と限界

- 改善できるのは文の中の問題である。活用形の違い、直接かかる否定、語彙の網羅。
- 文脈に依存する判断（「それでいこう」の「それ」が何か、直前に提案があるか）は、会話の状態を持つ決定グラフ側の設計で扱う。文の解析では直らない。
- 「不足している可能性」を問題とするかリスクとするか、のような正解の定義のあいまいさは、どのライブラリでも解けない。精度の上限は、人同士のラベルの一致率である。
- 世界知識（「落ちる」が悪い結果かどうかは主語による）、婉曲・皮肉、話し言葉の崩れも、規則・ライブラリ共通の限界である。

したがって、迷う発話を「迷う」と出すこと（断定しないこと）が、全体の精度を上げることより重要である。

## 結果・影響

- 推測の言い回しの違いで、結果が変わりにくくなった。
- 未対応の例は [STATE.md](../STATE.md) の「既知の未解決課題」に記録した。
- `npm run semantic:eval` は、決定グラフの推測・否定を測れない。この変更の評価には `npm run decision:eval` を使う。
- 評価データはリポジトリ外にあるため、保管先を別に決める必要がある。

## 保留した判断（提案）

1. 実データの収集: ライブマップのノードの高評価・役割と親の手動修正は評価 JSON に出力される（[STATE.md](../STATE.md)）。この出力が評価データとして使えるかは、未調査。
2. 分類の軸分解: 種類を1つ決める代わりに、変わりにくい軸（推測・否定・疑問・約束など）ごとに特徴を持ち、種類は後で組み合わせて決める。会議内容か雑談・進行かを別の軸（`scope`）にする。Semantic Core の軸（[ADR 0022](0022-semantic-core-and-central-promotion-policy.md)）と同じ方向。
3. 学習ベースの補助: 実データがたまったあと、ブラウザ内の小型エンコーダを、非同期の精緻化パス（ADR 0023）で、結果を未確認ノードとして持つ形で比べ直す。
4. 評価データの拡充: 提案・決定・質問・否定のケースを増やし、人が確認したラベルに置き換える。
