# 会議支援UI 設計・評価レポート

作成日: 2026-09-18

## 1. 結論

このアプリのUIの目的は、会議の内容をたくさん表示することではない。

> 会話を邪魔せず、必要な論点・未決定事項・危険な抜けを見逃さなくすること

したがって改善の優先順位は、色・余白・角丸ではなく、次の順にする。

1. 目的と利用場面を固定する
2. 情報を意味のまとまりに分ける
3. いま見るべき情報を一つに絞る
4. システムの状態と確度を明示する
5. 次の操作を迷わせない
6. 視覚表現を整える
7. 実際の会議で検証する

## 2. 対象ユーザーと中心タスク

主利用者は、画面を操作しながら会議を進めるファシリテーターである。参加者全員が常に画面を読む前提にはしない。

ファシリテーターが達成したいことは次の四つ。

- 今どの論点を話しているかを把握する
- 決まったことと、まだ決まっていないことを区別する
- 担当・期限・理由などの危険な不足を発見する
- 会話を止める価値がある確認だけを選ぶ

UIの成功は、表示情報の量ではなく、これらの判断にかかる時間と誤りの少なさで評価する。

## 3. 情報構造

会議情報は、少なくとも次の意味単位に分ける。

```text
会議
├── 現在の話題
│   ├── 発言
│   ├── 課題
│   ├── 理由・前提
│   ├── 提案・別案
│   └── 決定
├── 今すること
│   ├── 担当
│   ├── 期限
│   ├── 優先度
│   └── 実行状態
├── 未決定・未確認
├── 次に確認すること
└── 根拠発言
```

「発言」と「解釈」、「確認済み」と「推測」、「決定」と「提案」は同じ見た目のカードにしない。特にAIやルールから得た候補は、会話中に確定した事実として見せてはいけない。

## 4. 7層による評価

### 4.1 目的

画面を開いた瞬間に、利用者が「いま何を確認すべきか」を理解できる必要がある。主画面の中心メッセージは、全情報の一覧ではなく、現在の論点と次の判断にする。

評価質問:

- 10秒以内に現在の論点を言えるか
- 会話を止めるべき確認と、後でよい確認を区別できるか

### 4.2 情報構造

会議の進行、分析、入力・再生を分離しつつ、相互参照は保つ。現在の実装にある「進行」「分析」のタブと入力ドックはこの方向に合っている。

ただし、マップだけでは意味の種類と確度を読み取る負荷が高い。マップは関係の把握、右レールは判断、原文パネルは検証という役割分担を明確にする。

### 4.3 優先順位

画面の第一優先は「今すること」、第二優先は「未決定・危険な不足」、第三優先は「根拠」、第四優先は全発言の閲覧とする。

危険な不足の例は、担当なし・期限なし・理由なし・再開条件なしである。単なる未整理項目と同じ強さで表示せず、対応が必要なものだけを上位に出す。

### 4.4 状態設計

利用者は、アプリが現在どの状態にあるかを常に知れる必要がある。

- 議論中: 質問を割り込ませず、候補を内部または控えめに提示する
- 確認・改善中: 選別した質問を一件ずつ扱う
- 振り返り中: 決定理由・異論・持ち越しを確認する
- 解析中: ルール結果を表示し、AI処理中であることと待ち時間を示す
- 解析不能: 不明であることを明示し、安全性を主張しない

AI応答の有無で画面の意味が変わらないことが重要である。AIが失敗しても、ルールベースの結果と根拠を残す。

### 4.5 操作設計

会議中の主操作は一つに絞る。「確認・改善を始める」「次の質問」「回答を記録」「保留」の流れを迷わず進められるようにする。

「なぜ？」は決定 → 理由／リスク → 根拠 → 原発言の順で一段ずつ開く。詳細を最初から展開すると会話への注意が奪われるため、段階的開示を基本とする。

自動処理が行った変更には、必ず出典と確度を添える。自動で決定を確定したり、質問を音声で割り込ませたりしてはいけない。

### 4.6 視覚設計

視覚表現は意味構造を補強するために使う。色だけで状態を表現せず、ラベル・アイコン・線種・位置を併用する。

- 強調: 今見るべき一項目
- 警告: 担当・期限・理由などの不足
- 未確認: ルールやAIによる候補
- 確認済み: 発言または手動操作で確定した状態
- 参照: 根拠発言や過去の情報

長い日本語ラベルと短いラベルを同じレイアウト規則で確認する。マップの美しさより、選択した項目とその根拠の対応が一目で分かることを優先する。

### 4.7 検証

自己評価ではなく、代表的な会議シナリオで検証する。

- 話題が急に変わる
- 提案だけで決定されない
- 担当は決まるが期限が決まらない
- 複数案が比較される
- AIが未設定または接続に失敗する
- 発言が多く、画面にすべて収まらない

測定項目は、現在の論点を見つける時間、未決定の発見率、危険な不足の見逃し率、誤った決定扱いの件数、確認操作による会話中断の回数とする。

## 5. 現状評価

### 強み

- 会議モードを主モードとし、進行と次の検討を統合している
- 決定・理由・根拠・原発言を逆向きにたどれる
- 未確認の推測を決定として扱わない
- AIがなくてもルールベースで利用できる
- 質問の表示を利用者の明示操作に限定している
- 担当・期限・理由の不足を構造化データから検出できる

### 優先して確認する課題

1. 進行マップ、分析パネル、入力ドックのどれが現在の判断対象かが、状況によって競合しないか
2. 未決定・未確認・危険な不足の違いが、色や位置に依存せず伝わるか
3. 発言の追加やAI処理中に、利用者の閲覧位置や選択が奪われないか
4. マップ上で、現在の論点から次の確認項目へ移動できるか
5. 情報量が増えたとき、重要項目が埋もれないか

## 6. 改善ロードマップ

### フェーズ1: 意味と優先順位

- 「今すること」「未決定」「危険な不足」「根拠」の表示順を固定する
- 各項目に状態、確度、出典を明示する
- 会議中と確認・改善中の表示ルールを分ける

### フェーズ2: 操作と状態

- 次に行う主操作を一つに絞る
- 質問の選別理由と残り時間を表示する
- AI処理中・失敗・解析不能を同じ状態設計で扱う
- 自動更新時に閲覧位置を維持する

### フェーズ3: 視覚表現

- 状態ごとの色・ラベル・線種を整理する
- 長短ラベル、狭い画面、拡大表示でレイアウトを検証する
- 重要度と確度を別の視覚属性として表す

### フェーズ4: 実地検証

- 5種類以上の会議シナリオで操作テストする
- ファシリテーターが会話を止めずに確認できるか観察する
- 見逃しと誤検出を記録し、ルール・UI・操作のどこを直すか切り分ける

## 7. 設計原則

- 会話を止めるのは、重要度と緊急度が高い確認だけ
- 事実、推論、候補、未確認を混ぜない
- 情報を減らすのではなく、見る順番を設計する
- 自動化の結果には必ず根拠への道を残す
- AIは後処理層として使い、会議のリアルタイム進行を支配させない
- 見た目の一貫性より、意味と状態の一貫性を先に守る

このアプリのUI改善は、装飾の刷新ではなく「会議中の注意を、必要な判断へ正しく配分する設計」として進める。
