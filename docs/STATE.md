# Current State

最終更新日: 2026-09-16

## 現在できること

会議モードの進行タブには、ファシリテーターが任意の時点で実行する「判断材料を確認」がある。公開・導入などの実行文脈と不具合・品質への懸念が発言でそろう場合だけ、対応体制、公開範囲、速度と安全性の価値判断を候補として示す。候補は確認済み発言、規則による推論、会話からは不明な情報、条件付き仮説、根拠発言を分離し、推論の比較案を参加者の提案や決定として扱わない。処理済みの候補は同じ前提で再表示せず、根拠となる前提が変わった場合は再確認にする。根拠を十分に特定できない場合は「解析不能」と表示し、安全・漏れなしとは主張しない。方針は [ADR 0017](adr/0017-manual-decision-material-review.md)。

アプリの中心は会議の進行支援で、起動時は会議モードの中央パネルに「会議の状況」（`MeetingStateDashboard`）を開く。先頭には「現在地」カード（`CurrentDiscussionCard`、[ADR 0020](adr/0020-current-discussion-location-and-topic-title-safety.md)）を表示し、現在の論点、現在地（問題を確認中／原因・理由を整理中／選択肢を出している・比較中／未解決の問いを確認中／決定済み／実行内容を具体化中／実行中／複数の検討が進行中／状態を特定できません、のいずれかを既存の決定グラフから機械的に分類。常に「断定ではない」ことを明示）、未解決の問い、次に前進する条件（推定であることを明示するテンプレート文）、判断テーマ（決定が実在する場合のみ表示、無ければ「なし」）を一体で示す。論点タイトルは、抽出済みの議題→未解決の問い→直近発言→「論点を特定できません」の順でフォールバックし、助詞始まりなどの壊れた断片は表示しない。その下に、今決まっていること（確定した決定のみ）、確認が必要な項目（構造上の不足・未確認/未解決・追加で確認できることを区別。後者は`decisionSupport.ts`のルールベース処理の出力であり「AI」とは呼ばない）、次にやることを表示する。0件のセクションはコンパクトな折りたたみ表示にし、実際に存在する情報を優先する。項目の「根拠を見る」は同じ画面内で発言・時刻・発言者・参照先を表示し（状態と根拠の統合、[ADR 0019](adr/0019-meeting-state-evidence-unification-and-provenance-honesty.md)）、複数ホップの関係探索が必要な場合だけ「関係を詳しく見る（根拠マップ）」から旧`MeetingStateMap`を開く。構造上の不足は、実行段階（決定済み・実行中）のアクションだけを対象とし、まだ採用されていない提案には適用しない。従来の発言順マインドマップ「流れ・次の検討」（課題・理由・提案・別案・決定と、そこから生じる質問・条件付きの検討予定を表示し、確認・改善の時間配分機能を持つ）、「会話マップ」、「整理マップ」は削除せず、中央パネル下部の切替から引き続き開ける。画面上部から発言を追加でき、音声・リプレイも同じ状態に反映する。方針は [ADR 0015](adr/0015-live-meeting-progress-and-conditional-planning.md)、中央パネルの構成は [ADR 0018](adr/0018-meeting-state-primary-surface-and-epistemic-boundaries.md)・[ADR 0019](adr/0019-meeting-state-evidence-unification-and-provenance-honesty.md)・[ADR 0020](adr/0020-current-discussion-location-and-topic-title-safety.md)。以下のアイデア出しは補助モードとして引き続き使え、マインドマップを主役のまま維持する。

アイデア出しモードでは、日本語音声または手入力からキーワードを収集し、発言順の放射状マップに表示する。画面は上部のフェーズと残り時間、左レールの議題・進行操作、中央のマップ、右レールの自動保存メモ・手入力・AI 設定に分かれ、ファシリテーターが全体を一画面で把握できる。収集後はグループ化して、左から右へ「テーマ → グループ → キーワード」と進む一方向の階層マップに遷移し、グループ名を編集して各キーワードを採用・保留・却下に整理できる。Markdown とセッション JSON は3状態と出典発話を保持する。LLM 設定（LM Studio とモデル）は localStorage に永続化され、アイデア出しモードと会議モードで共有される。以前に保存された外部 LLM の接続先は起動時に LM Studio の既定接続先へ戻す。マップは自由にパン・ズームでき、常時表示される「全体を表示」で全ノードを画面内へ戻せる。

会議モードの空状態では「流れ・次の検討」マップに開始案内だけを表示し、空の React Flow ノードや会議中の操作群を重ねない。ブラウザー音声入力が使えない場合、「会議を始める」から手入力を開く。ライブマップも空の間はノード描画をせず、案内を表示する。会話マップの手動調整と議題診断は、必要なときに開く折りたたみ領域へ移した。

会議画面の配色はニュートラルな背景と面を基調にし、深緑を主要操作・選択状態に限定する。赤は実際のエラー、黄褐色は注意に限り、文字色は WCAG AA の通常文字コントラストを目標にする。配色面積は 60/30/10 を目安として扱う。

会議ダッシュボードには進行マップに加えて既存の分析機能がある。トピック抽出、カバレッジ追跡、Focus の手動選択・ロック、リプレイ、会議後の抜け漏れレポートと評価データ出力を備える。会議ライブマップはルールベースで相槌を除外し、発言を「話題 → 課題 → 原因 → アクション／別案」の右向き意味階層として即時表示する。「以上です」「今日はここまでです」などはノードにせず現在の話題を閉じ、その後の発言を会議ルート直下の新しい話題として開始する。各ノードは0/1の高評価を付けられ、選択後に役割と親を手動修正できる。高評価と親子関係はversion 2の評価JSONへ含まれる。既存の議題・カバレッジ分析はライブツリーと並行して維持される。会議画面は「会議の状況」「会議マップ」「今すること」の3領域で構成する。分析・レポート・設計仮説・診断・マップ調整は折りたたみ領域へまとめ、入力・再生ドックは初期状態で閉じる。進行タブの「NOW / 今すること」は、発話を保存した型付きの決定グラフから決定済みアクションを表示する。規則ベースで根拠・リスク・提案・決定・アクションを増分で接続し、カードの「なぜ？ 根拠を見る」から決定、理由／リスク、根拠、元発言へ逆向きにたどれる。AI はこのグラフを自動生成せず、未確認の推測は「未確認」として保持する。「確認・改善」で使う質問候補は、議題・決定済みアクション・未解決質問からルールベースで導出する。質問の提示は「流れ・次の検討」に集約し、他のマップでは確認・改善の進行へ戻るボタンを表示する。担当・期限などの不足は対象アクションを明記し、根拠発言を開ける。質問への回答は、誰・いつ・理由・決定を明示する肯定発言だけを接続する。会議後レポートとMarkdown出力にも「次回確認すること」を含める。「会議を整理」を押すと、規則ベースの整理マップを即時に作り、AI プロバイダーが設定されていれば根拠発言を保った議題統合・要点化で更新する。整理マップの「課題」「未解決」項目を選ぶと、その根拠発言と会議・議題・項目・発言 ID の参照を保ったままアイデア出しセッションを開始できる。AI の整理中は、発言数に基づく残り時間の目安と進捗バーを表示する。AI の応答は通常800トークン、会議整理は1200トークンに制限し、長すぎる生成で処理が占有されることを防ぐ。整理マップでは要点ごとに原文を開閉でき、議題・要点のタイトルだけをセッション中に修正できる。開発サーバーは `npm run dev`、アプリは `http://127.0.0.1:5173/`、ローカル WebSocket とログ・レポート APIは `http://127.0.0.1:8787` を使う。

会議モードには実験的な「設計仮説」タブがある（`design-hinge/` 配下の独立エンジン、詳細は [ADR 0010](adr/0010-design-hinge-engine-only-mvp.md)）。発話を因果グラフ（ノード・エッジ・確信度・検証状態）へルールベースで変換し、孤立ノードや低確信度エッジ、矛盾する因果関係、沈黙、同内容の繰り返しを検知して質問カードを提案する。カードは必ずユーザーが「表示する」を押すまで内部に留まり、自動音声出力は行わない。ノード・エッジは「確認済みにする」で承認、エッジは「取り消す」で削除できる。反実仮想ボタンは、その要素を取り除いた場合に到達性が失われるノードを一文で示す。セッションは `design-hinge_session` 形式で JSON 書き出しでき、`npm run shadow-replay` で過去セッションを別のポリシーパラメータで再評価できる（Shadow Mode）。手動発話・ファイル再生・音声入力のいずれからも同時に取り込まれる。

## 現在のフェーズ

決定グラフは一般的な「〜しましょう」「〜します」と「〜なので、〜」「〜だから、〜」の因果節も処理し、明示された担当・期限をアクションへ保存する。「なぜ？」は一段ずつ開き、原発言の全文・時刻・提供された発言者まで確認できる。未決定の提案・質問・未確認項目は折りたたみ表示する。疑問・否定・仮定の決定化を抑制し、明示的な話題転換前の根拠は接続しない。ただし近接発言によるヒューリスティックであり、暗黙の話題転換・複雑な否定・複雑な質問の自動解決・発言からの決定撤回・完了の自動反映は未対応（[ADR 0012](adr/0012-incremental-decision-reason-traversal.md)）。

会議がどう進み、考えがどうまとまったかと、その状態から次に何を確認するかを一体化する段階。放射状表示、グループ化後のマインドマップ、会議ライブマップ、進行・予定マップは長短ラベルの配置テストで保護する。製品判断は会議中の進行と検討の連動を優先する。利用形態はファシリテーター1人の操作と画面共有を前提とし、複数端末の同時編集は対象外とする。

### 会議の流れと条件付き検討計画（2026-09-11）

- 発言番号と任意表示の時系列線で進行順を追える。提案から採用への参照と、課題・理由からの関連候補を同じマップに表示する。A案・B案など明示された案名が一意なら採用した案へ接続し、他案の発言も残す。議題開始の「今日は〜について決めます」は決定済みアクションにしない。
- 発言追加とアクションの手動更新に応じて不足点を内部で再評価する。議論中は質問・条件付き予定を表示せず、AIの質問レビューも実行しない。「確認・改善を始める」で残り時間（1〜180分）を設定した後に質問を表示する。未確認の前提・未解決質問、決定、担当・期限の順で、1問約1分・最後の2分を振り返りに確保して選別する。回答・保留の後は次の質問を開く。時間外・保留は持ち越し候補に残す。マップには選別した質問の最大4件と選択中の問いを表示する。
- 問いに回答を記録すると元の問いへ回答線を付け、確認できた／追加確認が必要という選択に応じて次の検討項目を作る。保留・再検討・複数回答を保持する。回答の記録は担当・期限の自動確定ではなく、必要なら「今すること」で対象アクションを更新する。
- 音声で回答する場合は、問いの「次の発言を回答として接続」で回答先を指定する。次の1セグメントだけをその問いへ接続し、その後は通常の発言入力に戻る。指定は画面上部で解除できる。マップの「更新時に全体表示」を切り替えられ、項目選択時は選択位置へ移動する。
- 確認・改善中で質問に使える時間があり、LM Studioのモデル設定時は、時間内に扱う優先質問の最大3件を非同期に具体化する。入力は根拠・直近の発言最大16件（各600文字）、出力は1200トークン。3秒周期の更新確認、同時1件、20秒タイムアウト、古い版の応答の破棄によりライブ入力を継続する。AIが未設定・接続不可・形式不正ならルール提案を利用する。
- 時間スライダーで過去の発言時点まで戻れる。過去表示では現在の質問・予定を表示しない。過去のAI提案や当時の手動レイアウトを完全復元する機能ではない。
- 「流れ・予定をMarkdown出力」「出典付きJSON」は会議全体の発言・関連・問い・条件分岐・回答参照を含む。JSONは `meeting-progress` version 1。現在アクションの手動更新は進行マップにも結果の枝として現れる。DB・リロード復元はない。

- 残り2分、または「振り返り・最終確認へ」で、決定・変更・回答を振り返り、決定理由／認識のずれ・異論・前提／持ち越しの担当・期限・再開条件の3項目を手動記録する。時間切れは自動完了にしない。発言・アクション更新後は最終確認をやり直す。確認状態はマップ切替で保持し、会議リセットで議論中に戻る。確認結果は進行マップのMarkdown・JSONに含む。方針は [ADR 0016](adr/0016-explicit-time-budgeted-meeting-review.md)。

関連付けは引き続きヒューリスティック。AI応答より発言の更新が速い間はルール提案が表示される。ブラウザー音声認識と実際のLM Studioでの提案品質は利用環境で確認が必要。

LLM通信のモデル取得・実行結果、ローカルサーバーの起動、Discordレポート送信結果は、本文と秘密情報を除いた JSON Lines 形式で `logs/runtime-YYYY-MM-DD.jsonl` に記録する。ブラウザーのログはローカルサーバーの `/api/logs` が保存する。会議後レポートは、`.env` の `DISCORD_WEBHOOK_URL` を設定すると画面から Discord Webhook へ送信できる。

保守担当者向けの構成、変更手順、障害切り分けは [TECHNICAL_REPORT.md](TECHNICAL_REPORT.md) にまとめ、`npm run report:discord` でDiscordへ送信できる。

日常の運用手順と次担当者への記録項目は [HANDOVER.md](HANDOVER.md) にまとめる。

変更の検証は `npm run check` を基本とし、UI またはビルドに影響する変更では `npm run build` も実行する。会議の進行マップに状態マップ用のレイアウトクラスを誤適用しないようにし、進行マップの固定表示領域を維持する。

## 既知の未解決課題

「次に確認すること」の担当・期限・理由不足は、決定済みアクションごとの構造化フィールドから検出する。別アクションの担当決定や議題全体のカバレッジによって不足を隠さず、議題抽出ができなかったアクションも対象にする。処理はブラウザー内の純粋関数で、画面とレポートが共用する。WebSocket サーバーは中継のみで会議状態を所有しない。

- 放射状レイアウトの衝突回避は、セッション規模（数十キーワード）には十分だが、数百件規模では空間インデックスが必要になる可能性がある。
- キーワード・会議トピック・ライブ意味階層の抽出はヒューリスティックであり、状態はリロードで失われる。意味階層の誤判定は選択ノードの役割・親編集で修正できる。
- 音声入力はブラウザーの Web Speech API に依存する。ローカル WebSocket のログ中継は任意である。
- 「設計仮説」タブは実験段階であり、React Flow によるグラフ可視化はまだない（ノード・エッジは平坦なリスト表示のみ）。Shadow Mode の再評価は発話起点のトリガー（因果の飛躍・矛盾・同内容の繰り返し）のみを対象とし、沈黙トリガーは tick イベントを記録していないため再現できない。

### アクションの明示的な更新

NOWカードから担当・期限・優先度・実行状態と結果／変更理由を記録できる。対象IDを指定した純粋な状態遷移で更新し、完了・撤回は現在のアクションから除外する。結果・更新履歴からアクション、決定、根拠、元発言へたどれる。手動記録は操作担当者による記録として保持し、音声由来の発言には偽装しない。

### p.md の現在状態マップ（2026-09-11）

会議モードの「現在状態・根拠」へ切り替えると、今すること（担当・期限・優先度・実行状態）と未決定・未確認を一覧できる。項目の選択で、決定・理由・根拠・原発言へ一段ずつ進むReact Flowマップと原文全文を表示する。「一段戻る」「現在地点へ戻る」「全体を表示」を備える。すべての決定・課題・結果・発言は一覧から直接選択できる。従来の会話マップと整理マップも切替で利用できる。

決定エンジンは課題を型付きノードとして抽出し、根拠 → 課題 → 質問 → 提案 → 決定の逆参照も保持する。関連は近接発言を使ったルールによる候補であり、因果関係の証明とは扱わない。担当・期限・優先度はアクションの構造化属性として維持する。手動更新には変更前後の属性を保存し、完了・撤回から再開できる。提案に戻したアクションはNOWから除外し、未決定欄から再更新できる。

「状態をMarkdown出力」「出典付きJSON」は会議の任意の時点で利用できる。JSON（`meeting-state`, version 1）は全ノード・エッジ・原発言・更新前後の属性を含む。Markdownは現在アクション・未決定項目と全ノードの参照リンクを含む。DB保存・読み込み・音声録音は追加していない。

会議からアイデア出しへ切り替えても会議コンポーネントを維持し、戻ったときに状態を参照できる。非表示への切替時は会議の音声認識とファイル再生を停止する。ページの再読み込みでは状態は失われる。

アイデア出しモードでは、右レールに「アイデアの根拠と現在地」を常時表示する。収集、グループ化中、採用・却下の全フェーズで、任意のキーワードから採否・グループ・元発言・会議から引き継いだ場合の会議出典を確認できる。中央マップで選んだキーワードはこのパネルでも開く。確認操作は採否を変更しない。

## Semantic Core（2026-09-28）

発言の意味解釈を中央集約する移行が進行中（[ADR 0022](adr/0022-semantic-core-and-central-promotion-policy.md)・[ADR 0023](adr/0023-realtime-first-semantic-core-fast-and-refinement-paths.md)・[ADR 0024](adr/0024-realtime-budget-stages-and-speech-boundary-flush.md)）。`src/semantic/` に、生発言のイベントログ、1発話を0..N個の意味単位へ分ける分割、6軸（範囲・意味・発話行為・確定度・明示性・由来）の判定、差分更新のCanonical State、そして昇格を一箇所に集めたPromotion Policyを置く。Fast Path（発言確定直後・ルールのみ・局所文脈のみ）とRefinement Path（非同期）を分け、精度のためにリアルタイム性を落とさない。Refinement Pathは未実装（Phase 5）。

現在の適用範囲は「会話のタイムライン」だけである（`src/semantic/flags.ts` の `timeline`）。タイムラインは自分で分類をやり直さず、Semantic Coreの投影を表示する。1発話が複数の意味を持つ場合は意味単位ごとに分けて表示し、各単位が「会議の状況」へ昇格したかどうかと、その根拠が「規則が判定（未確認）」か「参加者が確認」かを区別して示す。分類の手動修正は軸ごとの部分上書きとしてイベントログに残るため、画面を切り替えても再解析しても失われない。修正と自動解析が食い違う場合は「自動解析と相違」として示し、自動側を勝たせない。

「会議の状況」「会話マップ」「決定グラフ」はまだ従来の実装のままで、利用者から見た動作は変わっていない（`flags.ts` の他のフラグは無効）。従来の分類器（`utteranceClassification.ts`・`conversationTree.ts`・`meetingDecisionGraph.ts`）は削除せず並存させ、Phase 6で重複を解消する。`npm run semantic:eval` が従来実装とSemantic Coreを同じcorpusで採点し、`npm run semantic:bench` がリアルタイム予算の消費率を報告する（テストではなくレポート）。

音声入力は、発言確定後の最大5000msの滞留を解消した。終端句読点があれば即時、無音約800ms、話し続けた場合の上限5000msで発言を取り込む（[ADR 0024](adr/0024-realtime-budget-stages-and-speech-boundary-flush.md)）。

### 決定グラフの基準ケース（2026-09-28）

決定グラフは「Xを決めます」を議題（決定ではない）、「Xで／に決定」「Xに決めます」を選択の決定として区別する。選択の決定はアクションを作らず、対象を含む直前の提案へ採用線を引く。「Xはどうかな」「Xもあったら」は質問ではなく提案、「〜し、いいと思う」「〜につながりそう」は理由、「鈴木くん、来週金曜までにXお願い」は担当・期限付きのアクション、「Xも作らないと」は担当・期限未定のアクションとして扱う。「現在の論点」は議題の発言（「今日は〜を決めます」）を最優先にし、「じゃあ」などの談話標識で始まる抽出結果は論点にしない。文化祭の13発言を `src/hooks/festivalGoldenMeeting.test.ts` の基準テストとして固定し、ストアから「会議の状況」までを通して検証する。「たぶん大丈夫じゃない？」のような推測は質問にも回答にもしない。「会議の状況」では未回答の質問・未確認を「未確認・未解決」、未採用の提案を「提案中（未採用）」として分けて表示する（`unresolvedItems` は両者の和として件数・評価用に維持）。現在地の判定範囲は議題の発言を起点にする。アクションの状態「決定済み」は完了と誤読されやすいため「実行予定」と表示し、根拠のない理由欄は表示しない。「会議の状況」でアクションの根拠を開くと、担当・期限と元の発言を同じ場所に表示する。判断材料は公開判断の5発言を `src/hooks/releaseDecisionMaterialsGolden.test.ts` の基準テストとして固定し、懸念がない場合や文化祭の会議では何も出さないことも検証する。

### 既知の未解決課題（Semantic Core）

- 「流れ・次の検討」マップ（`buildMeetingProgress`）は発言数に対して二次で増え、発話1600件付近でリアルタイム予算を超える。原因は `tree.nodes` × `graph.nodes` の入れ子で、Phase 4で解消する。`buildMeetingStateDashboard` も二次で、発話5000件付近で予算を超える。
- 昇格しなかった意味単位は捨てずに「未分類」として保持するため、件数が従来より多くなる。表示方法はPhase 3で扱う。
- corpusは20ケースで、実会議の録音を加えて広げる必要がある。
- 決定グラフの推測・可能性の判定（`meetingDecisionGraph.ts` の `TENTATIVE_PATTERN`）は言い回しに依存する。「可能性がある」「かもしれない」「と思う」は未確認の理由として拾うが、「と思います」「かもしれません」「考えられる」「おそれがある」「のではないか」は拾わない。拾った場合も、リスクや仮説が理由として出る。対応は [docs/tasks/hedged-expression-detection.md](tasks/hedged-expression-detection.md)（2026-10-04 記録）。
