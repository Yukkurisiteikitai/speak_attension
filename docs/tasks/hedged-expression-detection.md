# 作業指示書: 推測・可能性の表現の判定を言い回しに依存させない

想定実行: 単独セッション（ブランチを切って1つのPRにする）
ブランチ名の例: `fix/hedged-expression-detection`
PR: タイトル・本文は**英語**、タイトルは `fix:` などの接頭辞つき。決定グラフの判定以外（UI・他のパターン）は変更しない。

## 問題

決定グラフは発言を正規表現で種類（`reason` / `risk` / `problem` など）と状態（`unconfirmed` など）に分けている。推測・可能性を表す語の拾い方が**言い回しに強く依存**し、ほぼ同じ意味でも結果が変わる。

2026-10-04 に PR #19 のコードへ実際に流した結果（`appendMeetingDecisionSegment` に1発話だけ与えた結果。`utterance` 以外のノード）:

| 発言 | 現在の結果 |
|---|---|
| サーバーが落ちる可能性があります | `reason`（unconfirmed） |
| サーバーが落ちるかもしれない | `reason`（unconfirmed） |
| たぶん金曜日に公開できると思う | `reason`（unconfirmed） |
| サーバーが落ちることも考えられます | なし |
| サーバーが落ちるケースとしては考えられる | なし |
| サーバーが落ちるのではないか | なし |
| サーバーが落ちるおそれがあります | なし |
| サーバーが落ちると思います | なし |
| サーバーが落ちるかと | なし |
| サーバーが落ちそうです | なし |
| 金曜日に公開するのがいいかもしれません | なし |
| （参考）金曜日に公開しましょう | `proposal`（proposed） |

### 原因

1. **語彙が狭く、活用形に弱い。** `TENTATIVE_PATTERN = /(?:かもしれない|可能性|(?<!(?:いい|良い))と思う|としたら|場合は)/`。「と思う」は拾うが「と思います」は拾わない。「かもしれない」は拾うが「かもしれません」は拾わない。「考えられる」「おそれ」「のでは」「そう」は無い。
2. **推測語を含むと中身を問わず `reason` になる。** `isTentative || causal || benefit || /(?:原因|理由|なぜなら)/` の条件により、「落ちる可能性がある」のようなリスク・仮説も理由として出る。「会議の状況」の「未確認・未解決」に、理由ではないものが理由として並ぶ。
3. **リスク・問題の語彙も狭い。** `RISK_PATTERN` に「おそれ」「懸念」「かも」が無く、`PROBLEM_PATTERN` に「落ちる」が無い。そのため推測語の言い方を変えると、リスクとしても拾われない。

## 目的

- 推測・可能性の判定を、丁寧体・常体や言い換えの違いで結果が変わらないようにする。
- 推測を含む発言を、内容に合った種類（リスク・問題・理由）にし、`unconfirmed` として扱う。理由でないものを理由にしない。

## 方針（推奨。変更してよいが理由を記録する）

1. 推測語の判定を専用の純粋関数（例: `isHedged(text)`）に切り出し、`TENTATIVE_PATTERN` の直接参照をなくす。
2. 判定の前に語尾を正規化する（です・ます・ません・ない・られる の差を吸収する）。そのうえで語彙を足す: 「かもしれません」「思います」「考えられる」「おそれ」「懸念」「のでは」「そうだ」「かと」など。
3. 「いいと思う」は評価であり推測ではない、という既存の例外（`(?<!(?:いい|良い))`）は維持する。
4. 推測を含む発言の種類は、内容で分ける。悪い結果の可能性（落ちる・壊れる・遅れる等）は `risk`、事実の不足や不確かさは `problem`、因果の説明は `reason`。推測語があるだけでは `reason` にしない。
5. 判断に迷う発言は、種類を断定せず `utterance` のままにする。推測を決定・確定にすることは絶対にしない（AGENTS.md の制約）。

LLM は使わない。使う場合も非同期の後処理だけで、ルールの結果を置き換えない。

## やらないこと

- `src/utils/utteranceClassification.ts`（会話タイムライン側の別分類器）は変更しない。必要なら別の指示書にする。
- UIコンポーネント・表示文言は変更しない。
- 他のパターン（`DECISION_PATTERN`、`ASSIGNMENT_PATTERN` など）は、この課題に必要な範囲を超えて変更しない。
- 既存の基準テスト（`festivalGoldenMeeting.test.ts`、`releaseDecisionMaterialsGolden.test.ts`）の期待値を、通すためだけに変えない。

## 受け入れ条件

1. 上の表の12文について、同じ意味のものが同じ種類・同じ状態になる。期待値は実装前に決めてテストへ書き、決めた理由を PR に書く。
2. 「いいと思う」「それでいこう」など、推測でない発言が推測として扱われない（false positive を増やさない）。
3. 既存のテストがすべて通る。`npm run semantic:eval` の決定・アクションの precision / recall が悪化しない。
4. 追加テストは `src/utils/meetingDecisionGraph.test.ts` に、言い回しの組（丁寧体と常体、「と思う／と思います」、「かもしれない／かもしれません」など）で追加する。
